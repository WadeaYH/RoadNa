# RoadNa JO — current frontend review

Reviewed 15 October 2026. This review covers the current 27 screens and shared source, rather than the older checkpoints or design reference copies. The application remains a frontend prototype with independent sample records, preview roles and no persistence.

## Built in this pass

### Registration: formal resident access

Register displays its form immediately in a formal municipal portal layout. A restrained teal identity panel sits beside a white form area on desktop; phones show a single-column form. Clear headings, consistent field spacing, explicit labels and neutral surfaces replace the office experience.

The existing name, email, password, password confirmation and residency certification are preserved, with accessible inline errors, password visibility controls and a clear link to Login. No registration steps were added. Invalid submissions retain entered details and keep focus within the form.

The introductory office, character, camera movement, paper transition and unused illustration have been removed. Neither account page loads graphics resources or depends on WebGL. Existing query strings and the `#registration` anchor still lead directly to the form. Without JavaScript both forms remain readable and preview submission stays disabled, avoiding an accidental form GET containing credentials.

Implementation: `screens/login/{index.html,style.css,script.js}`, `screens/register/{index.html,style.css,script.js}`, `shared/account.css` and `shared/account.js`. The office module was removed. The landing story and CityWorld engine remain unchanged.

### Login: immediate access

Login uses the same formal layout and identity as Registration. The form appears at first paint. Resident/staff selection, routing, password recovery and all four preview destinations are preserved. Preview shortcuts remain in an expandable section. The registration link now clearly says “Create an account”.

### 3D map: operations statistics

A compact map summary now shows open reports, unassigned reports older than two hours and available crews. Statistics opens an accessible expandable section inside the existing panel, with visible/fixed counts, dispatch and repair averages, department workload bars and available/on-route/working/returning crew counts. No chart library was added.

Report statistics follow the selected department and shown statuses; crew availability follows the department. Both use the current shared simulated clock. Open reports include work awaiting verification. Dispatch duration runs from submission to first dispatch; repair duration runs from dispatch to the first completed-work event (check or fixed). Records without the necessary timestamps are excluded, and sample counts are visible. Returning crews are not available. The two-hour queue flag is explicitly a preview warning, not an SLA.

Area-card counts and average repair durations now use the same helper (`shared/ops-metrics.js`). Phone layouts keep the summary below the toolbar, the collapsed panel at the bottom and report details clear of the summary. Statistics remain limited to the existing supervisor/manager/super-admin operations view; the sandbox and resident screens are unchanged.

## 3D map: highest-value next changes

### 1. Use one report/work-order identity across the complete workflow

The operations map uses `RN-2025-*` reports. Team and supervisor samples use a separate work-order dataset with `RN-2026-*` report references. The map's “Check this work” action opens the verification page without identifying the chosen report. It can therefore display a different job.

Unify the preview records, keep report ID and work-order ID distinct, and pass the selected identity into review, assignment, team task and verification pages. This is the most important functional improvement: every map action should open exactly the item selected.

### 2. Make the clock authoritative for vehicle travel

The shared clock gives a team a route/site/returning phase, while the 3D view reconstructs vans from report-status events. A replay can say “On the way” while a van is already parked at work; a returning team may be hidden at the depot.

Use the existing street graph to build each trip once, then sample van position, heading, parking and return progress from the same clock. Preserve the actual street-driving vehicles. Avoid introducing another floating truck marker or straight-line vehicle animation.

### 3. Resolve pin overlap in screen space

Separating reports by 4.2 world units cannot guarantee readable pins after a camera rotation or at phone width. Keep the geographic/road anchor stable; cluster nearby projected pins when zoomed out, and expand a selected cluster with short leader lines. This avoids moving reports to invented locations merely to fit their icons.

### 4. Store the real category and neighbourhood explicitly

Currently department selects the rendered problem: every Roads report becomes a pothole, including a stuck signal. Parks reports become bin debris. Area metrics are then derived from the visually relocated problem's quadrant, which can assign a University Street report to Downtown.

Add explicit category and neighbourhood fields to reports. Use location data for area statistics and the scene position only for rendering. Add signal, pavement and tree visuals when useful, with a neutral report marker as the honest fallback for unsupported types.

### 5. Keep the default supervisor view focused

Keep the pleasant miniature city and real vans, but prioritize **waiting reports, overdue work and checks due**. Show detailed team/vehicle/member information on selection, rather than as permanent floating labels. Let managers opt into area cards and wall display. Manual camera movement should cancel “Follow the van”, with an obvious way to resume it.

## Other limits and follow-up suggestions

- Role selection and the 3D notice are UI previews, not authorization. Actual access and department scope must be enforced by the future backend.
- Report, crew, voting, notification and profile changes are local to each page. A cross-page walkthrough does not yet represent one shared state transition.
- Real street tiles depend on OpenStreetMap connectivity. External tiles were intermittently pending/unavailable during the scan; local assets and UI checks are separate from that dependency.
- Resident Arabic currently changes layout direction while much of the copy remains English. A complete Arabic/RTL content pass is still needed.
- The code has accumulated several page-specific sample datasets and appended CSS overrides. Consolidate shared records first, then remove superseded rules in a separate, focused cleanup.
